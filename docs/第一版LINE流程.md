# 第一版 LINE 流程規格

這份文件是 Make.com 情境「11 LINE 訊息（第一版）」的施工藍圖：寫明每一條路線怎麼觸發、要檢查什麼、寫入什麼、回覆什麼。

- QR 格式見 `QR編碼規則.md`。
- 資料表見 `../建置紀錄.md`。

## 共通規則

1. **先認人**：每則訊息進來，先用 LINE User ID 查「工作人員名冊」。
   - 查得到而且勾了啟用中：工作人員或志工。
   - 查不到：一般民眾。
2. **權限在 Make.com 再檢查一次**：每條工作人員路線都要檢查「啟用中」和「簽到狀態」，必要時也檢查「角色」。不能只靠選單把關。
3. **「所在開設」＝工作人員名冊的「派駐開設」**：簽到時寫入。之後的所有寫入都掛在這個開設底下，這樣各所的資料不會混在一起。
4. **用回覆，不用推播**：LINE 免費方案每月只有 200 則主動推播。
5. **一次只處理第一個 event**：沿用舊版的做法。
6. **多步驟的狀態**
   - 簡單的分支：把狀態放在 quickReply 的文字裡，按了就會帶回來。
   - 需要打字的步驟（例如報到時輸入姓名）：用名冊的「對話暫存」記住進行到哪一步。打「取消」可以中斷。
7. **看不懂的訊息**：回覆「請點下方選單，或洽現場工作人員」，不會沒有反應。

### 物資頁面（LIFF，第二版）

設定 `line.liff_id` 後，簽到後的「物資」、本所狀況的「物資」、號碼牌的「領物資」都改成打開物資頁面（`liff/supplies/`，放在 GitHub Pages）。上面 R30～R43 的聊天室流程仍保留，打字「物資」或「飲用水+20」照樣可用。

- **居民畫面**（2026-10-19 起）：號碼牌 QR 是 `?r=MLS-xxxxx`，掃了直接開居民畫面。空白牌出現報到表單（一次填完）；使用中顯示居民狀態和按鈕（領物資、外出、返回、離所），「領物資」直接切到發放並帶入領取人，發完回到居民畫面。畫面上的「掃描」可以連續掃下一張號碼牌或物資標籤。取代聊天室 R5、R6 的一個個小按鈕；聊天室流程仍保留給舊版號碼牌。
- 三種入口打開同一個頁面：選單按鈕（整張庫存表）、物資標籤 QR（`?item=SUP-xxxxx`，直接跳到該品項）、號碼牌領物資（`?tag=MLS-xxxxx`，帶入領取人、只能發放）。
- 頁面一次填多項、按一次確認；後端是 Make 情境「13 物資 API」，用表單格式送出（瀏覽器不會先送 CORS 預檢），欄位 `a` 是動作：

| 動作 | 誰可以用 | 做什麼 | 回應 |
|---|---|---|---|
| `load` | 在班工作人員 | 讀派駐開設的收容所品項 | `{ok, me, items}`（items 是 Notion 原樣的 properties_value） |
| `submit` | 在班工作人員 | 每項新增一筆物資異動紀錄（來源「LINE 表單」、備註「物資頁面：…」；發放時寫入領取人 `g` 與發放區域 `w`），請求編號重複就不再寫 | `{ok, results:[{itemId, stock}]}` 或 `{ok, duplicate:true}`；發放沒有領取人也不是公共用途（`u=public`）回 400 `no_recipient` |
| `resident` | 在班工作人員 | 號碼牌 → 居民姓名與在所狀態 | `{ok, found, residentId, name, status, tagStatus}` |
| `addItem` | 在班管理者 | 新增物資品項（物資代碼由頁面產生，期初庫存 0） | `{ok, itemId}`；不是管理者回 403 |
| `tagInfo` | 在班工作人員 | 號碼牌狀態；使用中時附上居民（姓名、年齡層、特殊關懷、在所狀態、預計返回、分配區域；志工不回傳姓名和特殊關懷；不回傳電話、證號、照護說明） | `{ok, state: none\|blank\|used\|void, role, staff, opening, openStatus, resident}` |
| `register` | 在班管理者、門禁組 | 報到：新增收容登記、號碼牌改使用中、新增進出紀錄（報到）；本所要「開設中」、號碼牌要是本所的空白牌 | `{ok, residentId}`；409 `not_open`／`tag_unusable` |
| `move` | 在班管理者、門禁組、志工 | `kind`＝外出（`hours` 小時後預計返回）／返回／離所（號碼牌回收失效）；各寫一筆進出紀錄 | `{ok, status}`；409 `bad_state`（狀態已被別人改過）／`tag_unusable` |

- 身分：頁面送 LIFF 的 Access Token，Make 先向 LINE 確認它屬於本系統的 LINE Login channel，再取得使用者編號查名冊（啟用中、上班中）。驗證失敗回 401，頁面只自動重試一次，之後顯示原因，不會無限重新整理。
- 發放一定要有對象：居民（掃號碼牌）或「公共用途」（補到廁所、公共區等）。物資標籤和號碼牌用同一個「掃描」鈕，先掃哪個都可以；兩個都有了才能確認。
  - 以最後掃到的號碼牌為準：掃錯了直接掃正確的那張，不用先取消。查不到或已離所的號碼牌不會換掉原本的領取人。
  - 一位家人可以代領全家，數量不設限（防弊之後再做，見畫布待解問題）。
  - 發完自動清空領取人，避免下一位的物資記到上一位身上。
- 發放超過庫存：頁面先擋；若兩人同時發放造成負庫存，頁面標示「請盤點確認」。入庫依流程由指定一人負責。

### 本所畫面（LIFF，2026-10-19 起）

現場頁面上方有三個分頁：**本所｜居民｜物資**。「本所」直接開啟的網址是 `liff/supplies/?v=ops`（`https://liff.line.me/<LIFF ID>?v=ops`）。限在班的工作人員（名冊「身分類別」＝工作人員）；志工屬勞務型，用一般介面，不使用本所畫面。

- **知道**：開設階段與燈號；在所／容量、外出、未返、需關懷、未結事件（緊急數）、缺人；點外出、未返、需關懷可展開名單；在班人員；待處理事項（緊急的排最上面，標示待認領、我負責或誰處理中）。
- **記錄**：底部「＋記錄事件」，一頁填完：類別（緊急事件、重大事件、人員相關、物資相關、設施環境、交班紀錄）、嚴重程度（依類別預設，可改）、說明。緊急或高會勾「需回報社會處」。居民畫面的「記錄這位居民的事件」會帶入相關居民。
- **處理**：點開事項可「我來處理」（負責人改成自己、處理中）、「追加紀錄」、「已解決」；每一步都附時間和姓名寫進「處理紀錄」。
- **整備中**：多一張整備清單（場地清潔、水電設備、安全檢查、寢具、醫療物資），每項按完成或有問題；五項都完成後，管理者可以送出整備完成（開設狀態改待核准）。之前回報「有問題」的項目，按完成時會一併標成已解決。
- 本版不處理居民反映：居民從聊天室送出的反映不列入待處理清單（聊天室的「未結反映」仍可查）。
- 後端和物資、居民畫面是同一個 Make 情境「13 現場頁面 API（物資・居民・本所）」（免費方案只能啟用兩個情境：11 和 13）；以下動作限身分類別＝工作人員，志工呼叫會回 403 `not_staff`：

| 動作 | 做什麼 | 回應 |
|---|---|---|
| `status` | 讀派駐開設的數字、在班人員、外出・未返・需關懷居民、未結事件和所有整備回報 | `{ok, me, opening, duty, residents, events}` |
| `report` | 新增現場日誌（`cat`、`sev`、`text`、相關居民 `g` 可空白） | `{ok, id}` |
| `update` | `id` 事件，`kind`＝claim／note／resolve，`text` 處理情形；只能處理本所的事件 | `{ok}`；403 `not_ours` |
| `prep` | 整備回報（`item`、`result`＝已完成／有問題、`text`） | `{ok}` |
| `prepDone` | 管理者送出整備完成；本所要在「整備中」 | `{ok}`；409 `bad_stage`；403 `not_manager` |

## Make.com 運算式的地雷（實測踩過）

- HTTP 模組（Make a request）遇到 4xx 會中斷整個執行（即使關掉「Evaluate all states as errors」），webhook 只回「Accepted」。要在該模組的錯誤處理路線放 Webhook response＋Ignore，才回得出錯誤訊息。
- LIFF 在 LINE 內取得的 ID Token 可能是過期的舊憑證；後端驗證身分改用 Access Token。

- **不能用正則字面值**（`/…/`）：整個情境會初始化失敗並被自動停用。要切字串請用 `split`；filter 的 `text:pattern` 不受影響。
- **彙整（Text aggregator）的換行放進 JSON 會不合法**：送給 LINE `makeApiCall` 前要用 `replace(x; newline; "\n")` 轉成兩個字元的 `\n`。
- **數字欄位不要寫純文字常數**：寫 `1` 會被當成字串、Notion 回 400，要寫成運算式 `{{1}}`。
- **Make 遇到空字串會略過不寫**：清空對話暫存時改寫「－」。

## 社會處那一端（Notion）

1. 建立災害事件。
2. 建立 3 筆收容所開設，狀態是「整備中」，並填好簽到代碼。
3. 在工作人員名冊指派派駐開設。
4. 收到「待核准」後，打開那一所的開設頁，看過整備回報日誌，把狀態改成「開設中」。
5. 撤收：改成「撤收中」，再改成「已撤收」，填好結案欄位。

> 核准之後，系統不會主動通知現場人員，因為推播次數有限。現場負責人可以按「本所狀況」確認是不是已經「開設中」。

## 演練方式：真人操作一條線，其他由 Claude 批次模擬

- 使用者只有一個 LINE 帳號，在名冊裡是「清華里活動中心」的管理者，親手用 LINE 跑完 R1～R7，證明整條鏈是通的。
- 其他兩所的工作人員、全部 30 位居民的大部分報到和進出，由 Claude 依同樣的格式直接寫入 Notion。這些資料的來源標示為「演練模擬」。
- 驗收時，兩種來源的資料在 Notion 上要長得一樣。

## 圖文選單（兩張，一樣大）

兩張都是 2500 × 1686 px，**上下兩列**（LINE 最常見的版型），**上列 3 格完全相同**，切換時只有下列會變。

| | 左 | 中 | 右 |
|---|---|---|---|
| 上列（兩張共用） | 收容所資訊 | 我要反映 | 緊急聯絡 |
| 下列：一般選單 | 工作人員（整列一個按鈕） | | |
| 下列：加乘選單 | 掃 QR（開 LINE 掃描器） | 本所狀況 | 簽退 |

- 一般選單由情境「12」設為所有人的預設選單，會蓋過 LINE 後台設定的那張。
- **綁定方式**：工作人員簽到時，依別名 `staff-plus` 把加乘選單綁給這個人；簽退時解除綁定，退回一般選單。
- **換圖**：圖片放在 Notion「系統素材：LINE 圖文選單」頁的左右兩欄（左欄一般選單、右欄加乘選單），各用欄裡最後一張圖。換完執行情境「12」。設計範本由 `python tools/make_richmenu.py --template` 產生。
